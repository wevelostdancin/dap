# BENCH-P7 — что изменилось после волн A–E

Замеры на той же машине, что и `BENCH.md` (MacBook, Apple silicon, JDK 21.0.13,
DuckDB 1.5.6), одиночные прогоны, монотонные часы. Числа — «до/после» одного и
того же сценария; протокол каждого замера указан рядом. Это не сравнение с
внешним oracle, а фиксация эффекта правок.

## 1. Чтение CSV и ingest

| Сценарий | До | После |
|---|---|---|
| `dap.csv_reader`, 2M×4, `run` + `/table` | 3976 мс | **116 мс** (34×) |
| 5M CSV (сценарий `BENCH.md` §4.1.1), `run` | 4298 мс | **39 мс** |
| heap peak на 5M | 2628 МиБ | **21 МиБ** |
| две ветви-источника, 5M | 1.27× | **1.69×** |
| `POST /v1/datasets`, XLSX 200k×10, `-Xmx256m` | OOM | **8.3 с**, heap 42 МБ |
| `excel_reader`, XLSX 200k×10, `-Xmx256m` | OOM | **1.9 с**, heap 57 МБ |
| `excel_writer`, 200k×10, `-Xmx256m` | OOM | **9.3 с** |

Причина: CSV и XLSX идут через DuckDB (`read_csv`) и чанковый `Appender`; в heap
больше не строится Arrow-таблица на весь файл. Плюс ingest-кэш стал
содержимым-зависимым и самовосстанавливается после битого Parquet.

## 2. Чтение результата (`/table`)

2M строк, план с `GROUP BY`, `limit=20`:

| Запрос | До | После |
|---|---|---|
| первая страница | 78 мс | 107 мс |
| повтор той же страницы | 65 мс, **другой порядок** | 7 мс, тот же порядок |
| `offset=20/40/60/80` | 65.7 / 70.9 / 64.9 / 65.9 мс | 4.1 / 4.6 / 4.2 / 5.4 мс |
| `offset=1 000 000` | 93 мс | 25.7 мс |

Первая страница платит одноразовую материализацию в `dap_page_*` (бюджет
`DAP_TABLE_MATERIALIZE_BUDGET_ROWS`, по умолчанию 4M строк); дальше страницы
детерминированы и дешевле в 10–15 раз. Порядок строк больше не меняется между
одинаковыми запросами — это исправление корректности, а не оптимизация.

## 3. Отчёты

HTTP-эквивалент `dap_report` (workflow + `run` + `/table` + `/profile`):

| Датасет | До | После |
|---|---|---|
| 2M×3 | 79.2 мс | **50 мс** |
| 200k×46 | 285 мс | **179 мс** |
| секция `metrics` на 1M строк | 81 мс (отдельный скан) | **12 мс** (переиспользует profile) |

`/profile` не регрессировал: 57–60 мс на 200k×46 против 63 мс до правок (stddev
считается только для отчётов, обычный `/profile` за него не платит).

## 4. Статистика на больших данных

Снят жёсткий cap 100 000 строк у `correlation`, `linear_regression`, `pca`:
они считаются из SQL-моментов (`n, Σx, Σy, Σxy, Σx², Σy²`), в Java остаётся
матрица `p×p`. 1M строк × 20 колонок: correlation 0.4 с, regression 2.4 с,
PCA 0.7 с. Kendall tau-b остаётся с явным лимитом 100 000 строк (попарные
сравнения не выражаются моментами) и подсказкой в ошибке.

## 5. Агентский контракт (MCP)

- Все табличные ответы проходят через компактное форматирование с
  `maxCellChars` (по умолчанию 200): ячейка 100 000 символов — было ~25 000
  токенов, стало ~83.
- `dap_profile.limit` удалён из схемы (движок его не читал).
- Промпты переведены на one-call инструменты; невыполнимый шаг в
  `profile_report` убран.
- CI запускает 225 MCP-тестов и `mcp_recipe_e2e.py`.


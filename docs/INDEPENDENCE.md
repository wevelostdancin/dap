# Независимость от KNIME: текущее состояние и план

Этот документ отвечает на два вопроса без маркетинга:

1. **Сейчас:** нужен ли DAP установленный KNIME? — Нет. Является ли DAP независимым от кода
   KNIME? — **Нет.**
2. **Потом:** что нужно, чтобы стало независимым, сколько это стоит и по каким критериям
   мы это признаем.

## 1. Кратко

| Утверждение | Статус |
|---|---|
| DAP работает без установленного KNIME | **Да**, runtime vendored внутри дистрибутива |
| DAP не требует сети и внешней БД для базовой работы | **Да** |
| DAP — самостоятельная реализация аналитического движка | **Нет** |
| DAP содержит только собственный код | **Нет**: в дистрибутиве 610 бандлов KNIME/Eclipse |
| DAP можно собрать и запустить без runtime KNIME | **Нет** |
| Полная независимость от кода KNIME | **Не достигнута** |

DAP — производная KNIME Analytics Platform 5.12 под GPLv3. `com.dap.engine` не содержит
кода узлов и не переписывает `org.knime.core`: он **линкуется** с ним и вызывает
`WorkflowManager`, `NodeFactory`, `NodeModel`, `BufferedDataTable`, `NodeSettings` и
внутренние классы диалогов. Поэтому формулировка «DAP не зависит от KNIME» неверна;
верна формулировка «DAP не требует установленного KNIME».

Пилотный нативный движок (`engine-native/`, артефакт `dap-native`) не меняет этот вывод
для основного дистрибутива: он собирается отдельно, не линкует `org.knime` и разобран в §11.

## 2. Что уже независимо

- **Поставка.** `runtime/knime` (610 бандлов, ≈662 МБ) входит в релизный артефакт/образ.
  Пользователь не ставит KNIME и не выбирает workspace.
- **Запуск.** Один JVM, headless, без дисплея, CEF, product-бандлов и update site.
- **Контракт.** HTTP `/v1` и MCP-адаптер не являются API KNIME; они наши.
- **Каталог и схемы.** `catalog/catalog.json` и 827 JSON-файлов схем — наши артефакты,
  полученные обходом extension point и рефлексией; их можно пересобрать без правок движка.
- **Эксплуатация.** Нет внешней БД, очереди, сети; состояние в памяти; сохранение — в
  каталог KNIME по явному запросу.
- **Лицензионная прозрачность.** GPLv3, NOTICE с источником и описанием изменений.

## 3. Что не независимо

| Зависимость | Где проявляется | Почему это важно |
|---|---|---|
| `org.knime.core` | компиляция `com.dap.engine`, исполнение workflow | нельзя собрать/запустить без runtime |
| `org.knime.core.ui` / workbench | регистрация узлов, Swing-схемы | тянет UI-классы, хотя GUI не нужен |
| `WorkflowManager` | создание/исполнение/сохранение | семантика и баги наследуются |
| `NodeFactory/NodeModel` | все 832 узла | поведение узлов — код KNIME |
| `NodeParametersInputImpl`, `SwingDialogSchema` | схемы и choices | рефлексия во внутренние API |
| Версия 5.12.0 | `runtime/`, `catalog/`, `schemas/` | обновление узлов = обновление runtime |
| GPLv3-производность | весь дистрибутив | обязанности по исходникам и изменениям |

Дополнительно: `runtime/knime/configuration` содержит абсолютные пути, которые
генерируются `scripts/gen-bundles-info.py`. Это не зависимость от KNIME, но зависимость
от корректной процедуры упаковки.

## 4. Правовой статус

- DAP распространяется под GPLv3.
- Бандлы KNIME — GPLv3 с дополнительными разрешениями KNIME по разделу 7 (см. `LICENSE`).
- EPL-компоненты Eclipse сохраняют свои лицензии; `LICENSE` и `NOTICE` фиксируют состав.
- `NOTICE` обязан содержать источник, предложение исходников и описание изменений DAP.
- Пока движок линкуется с `org.knime.core`, «полная независимость» невозможна не только
  технически, но и юридически: это производная работа.

## 5. Целевая архитектура замены

Цель — не «переписать KNIME», а сохранить HTTP-контракт и заменить исполняющий слой для
**core-сценариев**, оставив experimental как зону ограниченной совместимости.

### 5.1 Плоскость данных

- **Apache Arrow (Java)** — колоночные таблицы, словари, null-битмапы, zero-copy между
  узлами. Заменяет `BufferedDataTable`/`DataCell` на границе исполнения.
- **DuckDB (JDBC)** — реляционные операции: фильтры, join, group-by, сортировки, SQL.
  Локальный in-process, без сервера.
- **Polars (Python sidecar, опционально)** — тяжёлые dataframe-операции и оконные функции,
  если JVM-реализация дороже. Обмен через Arrow IPC; sidecar не обязателен для базового
  профиля.
- **Собственный слой типов** — явные правила для missing values, дат/времени, decimal,
  строк и коллекций. Это главный источник расхождений, а не «математика».

### 5.2 Исполнение

- Собственный DAG-планировщик: топологическая сортировка, ленивые/жадные материализации,
  кэш промежуточных таблиц, отмена и таймауты — те же состояния job, что сейчас.
- Собственный реестр узлов и ABI: `id`, порты, конфиг-схема, функция исполнения.
- Совместимый JSON-контракт настроек: миграция со `settingsXml` на нормализованную схему
  с явным маппингом для core-узлов.
- Профилирование и превью — из Arrow без копирования в строки.

### 5.3 Совместимость

- `/v1`, MCP-инструменты и коды ответов остаются неизменными.
- `catalog/catalog.json` и `schemas/*.json` генерируются новым каталогом; поле `tier`
  сохраняется.
- Сохранённые KNIME workflow (`save`) — формат экспорта, а не внутренний формат DAP.
  Чтение чужих KNIME workflow в цели не входит, пока не доказана потребность.

## 6. Этапы

Оценки — для команды 3–5 инженеров, знакомых с JVM и аналитическими движками. Это
**оценка, а не обязательство**; этапы могут пересекаться.

| Этап | Содержание | Выход | Оценка |
|---|---|---|---|
| 0. База | заморозить `/v1`, собрать корпус golden-workflow, зафиксировать семантику типов и missing | контрактные тесты, baseline-метрики | 1–2 мес |
| 1. Данные | Arrow-таблицы, типы, конвертеры CSV/Parquet/XLSX, превью/профиль | чтение/запись и профиль без KNIME | 3–4 мес |
| 2. Ядро | DAG, job-модель, реестр узлов, конфиг-схемы, отмена/таймауты | исполнение 10 пилотных узлов | 4–6 мес |
| 3. Core-узлы | волны по категориям: IO → manipulation → aggregation → analytics; dual-run против KNIME | 141 core-узел с parity-тестами | 9–15 мес |
| 4. Схемы | собственная модель полей/choices, независимая от `NodeParameters` | 733 схемы или явные fallback | 4–6 мес |
| 5. Cutover | переключение default runtime, удаление `org.knime.*` из `engine`, финальный license scan | сборка и запуск без runtime | 2–3 мес |

Суммарно: **~24–36 месяцев** до заявки на независимость core-профиля. Это не «одна
неделя рефакторинга»: 832 узла и 3189 полей — это продукт, а не библиотека.

### Этап 0 — база

- Заморозить публичные схемы `Job/Workflow/Node/DialogSchema/Error`.
- Собрать 30–50 реальных workflow, покрывающих core-категории.
- Зафиксировать правила: missing, типы чисел, даты/таймзоны, строки, сортировка, округление.
- Ввести метрику parity: схема + значения + null-семантика + коды ошибок.

**Критерий выхода:** baseline-прогон воспроизводим на чистой машине; известен список
расхождений, которые нельзя исправить без замены движка.

### Этап 1 — данные

- Arrow Java как in-memory формат; конвертеры из CSV/Parquet/XLSX.
- Профиль (missing/distinct/min/max/mean) и превью — на Arrow.
- Кодировки, разделители, кавычки, типы — по корпусу этапа 0.

**Критерий выхода:** таблица из 10 млн строк читается и профилируется без KNIME;
результаты совпадают с baseline на корпусе (кроме задокументированных расхождений).

### Этап 2 — ядро исполнения

- DAG, состояния job, отмена, watchdog, лимиты.
- Реестр узлов: id, порты, схема конфига, исполнитель.
- 10 пилотных узлов: CSV Reader, Column Filter, Row Filter, GroupBy, Joiner, Sorter,
  Missing Value, String Manipulation, Math Formula, Excel Reader.

**Критерий выхода:** пилотный workflow исполняется end-to-end, API-контракт не меняется,
job-модель проходит тесты на таймаут/отмену.

### Этап 3 — core-узлы

Волны:

1. IO и файлы.
2. Манипуляции со строками/колонками.
3. Агрегация, join, сортировка.
4. Аналитика: статистика, регрессия, деревья, кластеризация.
5. Loop/flow-control.
6. Прочее, что попало в core.

Для каждой волны: реализация → parity-тест → dual-run → переключение tier.

**Критерий выхода:** все 141 core-узел имеют golden-тест и parity-отчёт; расхождения
либо исправлены, либо явно исключены из core.

### Этап 4 — схемы

- Собственная модель `DialogSchema`: поля, типы, умолчания, enum, динамические choices.
- Генерация из деклараций узлов, а не рефлексией по KNIME.
- Сохранение текущих ключей ответа, чтобы агенты не переписывались.

**Критерий выхода:** для core-узлов схема строится без `org.knime.*`; fallback остаётся
только для experimental.

### Этап 5 — cutover

- `com.dap.engine` не импортирует `org.knime.*`.
- `runtime/knime` не требуется для сборки и запуска.
- `make build-engine`/`make run` работают на чистой машине без KNIME.
- License scan: в дистрибутиве нет GPL-кода KNIME; остаются Arrow (Apache-2.0),
  DuckDB (MIT), Eclipse-независимые зависимости.
- OCI-образ меньше и стартует быстрее (цель: <200 МБ, <10 с до health).

## 7. Риски

| Риск | Вероятность | Влияние | Смягчение |
|---|---|---|---|
| Семантика типов/missing не совпадёт | высокая | высокое | этап 0, differential-тесты, явные правила |
| 150 узлов окажутся глубже, чем кажется | высокая | высокое | волны, приоритет по реальным workflow, tier experimental |
| Динамические choices завязаны на UI-фреймворк | высокая | среднее | собственная модель + fallback |
| Форматы (XLSX, Parquet, PMML, модели) | средняя | высокое | отдельные конвертеры, не тащить всё в core |
| Dual-run требует KNIME как oracle | высокая | среднее | oracle только на этапах 0–3, заморозить версию |
| Лицензионная неопределённость при поэтапной замене | средняя | высокое | юридический review, NOTICE, не смешивать кодовые базы |
| Производительность Arrow/DuckDB на JVM | средняя | среднее | бенчмарки на корпусе, Polars sidecar как опция |
| Команда/сроки | высокая | высокое | не обещать даты; gates, а не календарь |
| Соблазн «поддержать все 832 узла» | высокая | высокое | core = 150, experimental = best effort |
| Регрессия API при смене движка | средняя | высокое | контрактные тесты `/v1` в CI |

## 8. Критерии независимости

Считаем независимость достигнутой, только когда одновременно выполнено:

1. **Сборка:** `make build-engine` на чистой машине без `runtime/knime` и без KNIME.
2. **Запуск:** `make run` поднимает сервис без `org.knime.*` в classpath.
3. **Код:** `engine/` не содержит импортов `org.knime.*`; `grep` в CI это проверяет.
4. **Контракт:** все операции `/v1` и MCP-инструменты проходят контрактные тесты.
5. **Core:** 141/141 core-узел имеет golden-тест и parity-отчёт; известные расхождения
   перечислены и не входят в core.
6. **Данные:** корпус этапа 0 проходит с задокументированной точностью (значения, null,
   типы, коды ошибок).
7. **Лицензии:** в дистрибутиве нет GPL-кода KNIME; `LICENSE`/`NOTICE` отражают новый состав.
8. **Эксплуатация:** cold start < 10 с, образ < 200 МБ, нет регрессии job-модели.
9. **Dogfood:** 90 дней эксплуатации без runtime KNIME на реальных сценариях.

Пункты 1–3 — техническая независимость; 6–9 — продуктовая. Без 9 это «демо», а не замена.

## 9. Чего мы не обещаем

- Совместимость со **всеми** 832 узлами KNIME.
- Чтение произвольных чужих KNIME workflow.
- Побитовую совместимость результатов там, где KNIME зависит от UI/локали/версии.
- Замену KNIME как desktop-продукта.
- Дату завершения. Только этапы и критерии.

## 10. Что делать сейчас

1. Не писать в README «не зависит от KNIME» без оговорки о производности.
2. Держать `NOTICE` и `LICENSE` в актуальном состоянии.
3. Вести parity-корпус и метрики с этапа 0 — без них замена превращается в веру.
4. Обновлять `runtime` вместе с security-фиксами KNIME, пока зависимость не снята.
5. Фиксировать каждое изменение контракта `/v1`: это единственное, что переживёт замену.

## 11. Нативный движок (dap-native)

`engine-native/` — отдельный артефакт `dap-native` (один shaded jar, ≈44 МиБ), который
реализует замороженный контракт `/v1` без KNIME: Javalin 6.7 + DuckDB 1.5.6 + Arrow 19,
собственный каталог из 11 JSON-спеков (`dap.*`) и собственные исполнители узлов.

### 11.1. Граница зависимостей

- **Нет `org.knime`.** `grep -r "org.knime" engine-native/` пуст — это проверяет
  `make lint` (`scripts/check_repo.py`); в собранном `dap-native.jar` классов `org/knime`
  также нет.
- **Нет vendored runtime.** `engine-native` не читает `runtime/knime` и
  `catalog/catalog.json`; сборка и запуск не требуют этих каталогов.
- **Один артефакт.** `engine-native/target/dap-native.jar` — ≈44 МиБ, вместе с одной
  платформенной native-библиотекой DuckDB; лимит 50 МиБ проверяется в `make lint`, когда
  jar собран.
- **Сторонние зависимости.** DuckDB JDBC (MIT), Apache Arrow vector/memory (Apache-2.0),
  Javalin (Apache-2.0), Eclipse Jetty (EPL-2.0 или Apache-2.0), Jackson (Apache-2.0),
  SLF4J (MIT), Logback (EPL-1.0 или LGPL-2.1). JUnit 5 (EPL-2.0) — только test scope.
  Перечень с ссылками — в `NOTICE`, раздел 2.

### 11.2. Что это значит для GPL/EPL

- `dap-native.jar` не содержит кода KNIME и не является производной `org.knime.core`;
  лицензионные обязательства KNIME-рантайма (разделы 3–4) к нему не относятся.
- Сам DAP распространяется под GPLv3. Лицензии зависимостей native — MIT, Apache-2.0,
  EPL-2.0 (Jetty) и EPL-1.0/LGPL-2.1 (Logback); JUnit 5 (EPL-2.0) в артефакт не входит.
- Легаси-движок `engine/` остаётся связанным с `org.knime.core` (EPL). Два артефакта
  различаются по составу и лицензионным обязательствам, хотя собираются из одного
  репозитория.

### 11.3. Что остаётся общим

- **Контракт `/v1`.** `api/openapi-v1-frozen.yaml` и его `.sha256`; native его не меняет,
  `make lint` сверяет контрольную сумму.
- **Конвенции каталога.** id `dap.<type>`, tier (`core`/`experimental`), JSON-схема узла и
  форма `/dialog`. Native читает свои `specs/*.json`, а не `catalog/catalog.json`.
- **Parity-корпус.** `tests/corpus/*.json` и `tests/parity.py` — один корпус и одни правила
  сравнения для oracle (KNIME) и native.

### 11.4. Пределы утверждения

- Семантика узлов следует конвенциям KNIME (имена, типы, missing/NULL, сортировка), а
  корпус сравнивает native с oracle. Это совместимость поведения, а не общий код.
- Код KNIME не линкуется и не поставляется в `dap-native.jar`; `org.knime` в
  `engine-native/` отсутствует.
- Фаза 3 закрыта: 11 спеков, все 11 исполнителей (10 пилотных + `column_renamer`),
  parity 13/13; production-default пока остаётся за KNIME-движком. Статус и границы —
  [NATIVE.md](NATIVE.md), [ROADMAP-NATIVE.md](ROADMAP-NATIVE.md).

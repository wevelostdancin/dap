# Стратегия: DAP как лучший выбор для аналитики у агента

**Дата:** 2026-11-15 · **Статус:** рабочий документ · **База:** 1.1.0 + one-call инструменты

## 1. Где агент теряет время и токены (замерено)

Эксперимент на реальной выписке (306 строк):

| Путь | Вызовов | Время | Байт ответов (≈токены) |
|---|---|---|---|
| Ручная сборка графа (старый путь) | 25–47 | 2–4 с (холодный) | ~12–15 КБ |
| Один вызов `dap_analyze` | **1** | 3,0 с (вкл. cold start) | 1,4 КБ |
| Один вызов `dap_workflow_build` (6 запросов) | **1** | 84 мс (прогретый) | 4,5 КБ |
| pandas «с нуля» (при готовом окружении) | 3–4 | 0,18–0,32 с | — |

Вывод: потери — не в вычислениях (SQL 20–80 мс), а в **количестве шагов** и **объёме
ответов**. Значит, скачок даёт не ускорение движка, а сокращение вызовов и токенов.

## 2. Что уже сделано (этот коммит)

- `dap_analyze`: файл/датасет → таблица + профиль (+ опциональный SQL по `src`) за 1 вызов.
- `dap_workflow_build`: узлы + связи + запуск + таблицы выходов за 1 вызов.
- `sql_query.inputs` больше не обязателен: входы доступны под id узлов (`FROM "1:1"`),
  явные имена — опция; ошибка «алиас не тот» исчезла из типового сценария.
- Документация и тесты обновлены (28 инструментов).

## 3. Следующий порядок по эффекту

### 3.1. Один вызов на типовую задачу (эффект: ×10–20 по вызовам)
- `dap_profile` — компактный профиль файла/таблицы без графа (сейчас `dap_analyze` уже
  возвращает профиль; нужен короткий режим только профиля).
- `dap_report` — таблица + markdown + график за 1 вызов (обёртка над markdown_report/chart).
- Встроенные рецепты: `profile_report`, `quality_check`, `monthly_trends`, `top_categories`;
  `dap_recipe_suggest(file)` — подобрать рецепт по схеме файла.
- Промпты и описания инструментов должны вести агента к `dap_analyze`/`dap_report`,
  а не к ручной сборке графа.

### 3.2. Экономия токенов (эффект: ×2–5 по объёму)
- Таблицы по умолчанию 20 строк; отдельный `mode: summary` (rows, columns, head 5).
- Компактный профиль: только имя, тип, missing, distinct, min/max/mean; без дублей.
- Ошибки без эха всего SQL/тела; `hint` вместо стека.
- Ответы с `bytes`/`rows`/`truncated`, чтобы агент понимал цену вызова.

### 3.3. Валидация до запуска (эффект: −1 круг на ошибку)
- Проверка колонок/типов в `settings` при add/patch (schema-aware), а не на run.
- `dap_validate_workflow` — сухой прогон графа без материализации.
- Явные коды ошибок уже есть; добавить `field`/`expected` в тело.

### 3.4. Тёплый старт и кэш (эффект: −1–2 с на первом вызове)
- При старте движка выполнить прогрев (DuckDB-сессия + маленький SQL), чтобы JIT не
  оплачивался первым анализом (сейчас первый прогон ~2 с, прогретый — 26 мс).
- Кэш планов/таблиц по хэшу конфига (повторный `/table` не пересчитывает).
- AppCDS для JVM (отдельная задача, если прогрев не хватит).

### 3.5. Наблюдаемость для агента
- `dap_stats` — счётчики: вызовы, время, байты, кэш-хиты; чтобы измерять эффективность
  прямо в работе, а не экспериментом.

## 4. Целевые метрики (приёмка скачка)

| Метрика | Сейчас | Цель |
|---|---|---|
| Вызовов на типовую задачу | 1–2 (новый путь) / 25 (старый) | 1–2 |
| Байт ответа на задачу | 1,4–4,5 КБ | < 4 КБ |
| Первый ответ (холодный) | 3,0 с | < 1,5 с |
| Первый ответ (прогретый) | 84 мс | < 100 мс |
| Ошибок на задачу | 0 | 0 |
| Зависимостей у агента | 0 | 0 |

## 5. Порядок работ

1. Валидация one-call инструментов (ревью движка/адаптера, бенчмарк, доки) — в работе.
2. `dap_report` + `dap_profile` + встроенные рецепты и промпты (1 вызов на отчёт).
3. Токен-экономия: summary-режимы, компактный профиль, лимиты по умолчанию.
4. Schema-aware валидация и `dap_validate_workflow`.
5. Тёплый старт + кэш планов; замер до/после.
6. `dap_stats` и повторный эксперимент на выписке/100k CSV как приёмка.

## 6. Статус после реализации (2026-11-15)

Сделано из плана: one-call примитивы (`dap_analyze`, `dap_workflow_build`), `dap_report`
(таблица + markdown + график за вызов), `dap_profile` (только профиль), валидация
аргументов до запуска движка, прогрев движка на старте и ожидание прогрева адаптером.

Замеры после реализации (выписка 306 строк, холодный движок):

| Метрика | Было | Стало |
|---|---|---|
| Вызовов на разбор | 18 | **1–2** |
| Первый `dap_analyze` | 2,86 с (без прогрева) | **2,27 с** (прогрев + ожидание) |
| Второй `dap_analyze` | 1,7–2,3 с (JIT) | **25 мс** |
| `dap_report` (таблица + .md + .svg) | — | **43 мс**, 883 Б |
| `dap_profile` (только профиль) | — | **16 мс**, 824 Б |
| `dap_analyze` (таблица + профиль) | — | **1,26 КБ** |

Что осталось для следующего скачка: первый вызов всё ещё платит ~1,5 с за инициализацию
DuckDB JDBC (нужен AppCDS/постоянный движок); схема-зависимая валидация колонок до run;
кэш планов; `dap_stats` для измерения эффективности в работе.

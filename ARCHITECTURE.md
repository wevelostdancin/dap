# Архитектура DAP

Документ описывает, как устроен DAP 1.0.0: слои, процессы, модель заданий, сессии,
каталог узлов и границы, за которые движок сознательно не выходит. Контракт HTTP —
[docs/API.md](docs/API.md); зависимость от KNIME и план замены — [docs/INDEPENDENCE.md](docs/INDEPENDENCE.md).

## 1. Контекст

DAP — резидентный JVM-сервис для агентов. Он не хранит проекты и не имеет GUI. Его задача —
за минимальное число вызовов дать агенту возможность:

1. найти узел и понять его настройки;
2. собрать workflow;
3. выполнить его с контролем времени и отменой;
4. прочитать результат и статистику;
5. при необходимости сохранить workflow на диск.

Всё остальное — инфраструктура вокруг этих пяти шагов.

## 2. Слои

| Слой | Где | Ответственность |
|---|---|---|
| Vendored runtime | `runtime/knime` | OSGi/Equinox, `org.knime.core`, 610 бандлов, узлы, типы данных |
| Engine | `engine/src/main/java/com/dap/engine` | каталог, схемы, workflow, jobs, HTTP |
| HTTP API | `DapService` | маршрутизация, JSON, коды ответов, сессии |
| Адаптер MCP | `adapters/mcp/dap_mcp.py` | stdio JSON-RPC 2.0 → HTTP, без вычислений |
| Артефакты каталога | `catalog/` | `catalog.json`, `curated.json`, `schemas/*.json`, отчёт аудита |
| Сборка/эксплуатация | `scripts/`, `Makefile`, `deploy/` | сборка runtime/engine/каталога, запуск, OCI |

`com.dap.engine` — единственный собственный бандл. Он объявляет зависимости от
`org.knime.core`, `org.knime.core.ui`, `org.knime.core.util`, Equinox и Jackson
(см. `engine/META-INF/MANIFEST.MF`). Никаких других приложений внутри JVM нет.

## 3. Схема

```text
                       MCP-клиент / агент / скрипт
                                  │
                    stdio JSON-RPC 2.0 (tools/call)
                                  │
                    ┌─────────────▼─────────────┐
                    │ adapters/mcp/dap_mcp.py   │  тонкий транспорт
                    └─────────────┬─────────────┘
                                  │ HTTP/1.1, JSON
        ┌─────────────────────────▼──────────────────────────┐
        │ JVM (Eclipse Equinox, -application com.dap.engine.service)
        │                                                    │
        │  DapService (com.sun.net.httpserver)               │
        │   ├─ session(X-DAP-Session)                        │
        │   ├─ NodeCatalog ── catalog/catalog.json (v7)      │
        │   ├─ Tiers ──────── catalog/curated.json           │
        │   ├─ DialogSchema ─ catalog/schemas/*.json         │
        │   ├─ WorkflowManager.ROOT ── workflow-объекты      │
        │   └─ JobManager                                    │
        │        ├─ worker: 1 поток (исполнение)             │
        │        └─ watchdog: таймауты                       │
        │                                                    │
        │  KNIME core: NodeFactory/NodeModel, BufferedDataTable
        └─────────────────────────┬──────────────────────────┘
                                  │ classpath / OSGi
                    ┌─────────────▼─────────────┐
                    │ runtime/knime (vendored)  │
                    │ 610 бандлов, ~662 МБ      │
                    └───────────────────────────┘
```

Потоки данных: `BufferedDataTable` остаётся в JVM. Наружу уходят только JSON-представления:
строки (`toString` ячеек), имена/типы колонок, профиль. Никакой сериализации таблиц между
процессами нет.

## 4. Процессы и потоки

Один процесс ОС, один JVM. Внутри:

| Поток | Роль |
|---|---|
| main / OSGi | запуск приложения, инициализация CorePlugin, HTTP-сервер |
| HTTP-диспетчер (`sun.net.httpserver`) | приём запросов; executor по умолчанию выполняет обработчик в диспетчерском потоке, поэтому запросы обрабатываются **последовательно** |
| `dap-job-worker` | единственный worker, исполняет workflow; daemon |
| `dap-job-watchdog` | таймауты jobs; daemon |
| KNIME worker-потоки | создаются `WorkflowManager` на время исполнения узлов |

Практическое следствие: синхронный `POST /run` занимает HTTP-диспетчер на всё время
исполнения. Пока он ждёт, `GET /v1/health` и другие запросы не обслуживаются. Для
параллельной работы агент должен использовать `POST .../jobs` (202) и опрашивать
`GET /v1/jobs/{id}` — но сами workflow всё равно выполняются по одному.

### Холодный старт

1. Equinox поднимает бандлы и вызывает `com.dap.engine.service`.
2. `DapService` инициализирует `CorePlugin` и (если найден) `org.knime.workbench.core`.
3. Загружается `catalog.json` (или строится заново при отсутствии/несовпадении версии кэша).
4. Применяются tiers из `curated.json`.
5. Создаётся `JobManager`, HTTP-сервер начинает слушать.
6. При **первом** обращении к `WorkflowManager` OSGi распаковывает части бандлов в
   `runtime/knime/configuration/org.eclipse.osgi`. Это может занять десятки секунд.

Если запрос на создание workflow придёт в момент распаковки, статическая инициализация
`WorkflowManager` может упасть с `NoSuchFileException` (например, ещё нет
`.../lib/schemas.jar`), а JVM — «отравить» класс `NoClassDefFoundError` до перезапуска.
Наблюдалось на первом старте с пустым configuration-кэшем. Операционное правило: после
`/v1/health` прогреть сервис одним create/delete workflow и только потом пускать трафик;
при `NoClassDefFoundError` — перезапустить процесс. Подробнее — [docs/OPERATIONS.md](docs/OPERATIONS.md).

## 5. Job-модель

`JobManager` — единственная точка исполнения. Каждый запуск workflow становится job:

```text
        submit()
           │
           ▼
        ┌───────┐   worker взял   ┌─────────┐
        │ queued│───────────────▶│ running │
        └───┬───┘                └────┬────┘
            │ cancel() до старта      │
            ▼                         ├── task ok ──────▶ succeeded
        cancelled                     ├── task throw ───▶ failed
                                      ├── Interrupted ──▶ cancelled
                                      └── watchdog ─────▶ timeout
```

Состояния: `queued`, `running`, `succeeded`, `failed`, `cancelled`, `timeout`.
`timeout` выставляется флагом: если watchdog сработал, а задача успела вернуть результат,
финальное состояние всё равно `timeout`.

На практике прерывание не всегда даёт `cancelled`/`timeout`: `executeWorkflow` оборачивает
`InterruptedException` в `RuntimeException`, поэтому отмена или watchdog могут завершиться
как `failed` с `InterruptedException`. Тесты (`tests/golden/jobs.py`) допускают оба
терминальных состояния и фиксируют это как известное поведение.

### Поля job

| Поле | Смысл |
|---|---|
| `id` | `job-N`, глобальный счётчик в памяти |
| `workflow` | `wf-N`, к которому относится запуск |
| `state` | одно из состояний выше |
| `createdAt`, `startedAt`, `finishedAt` | миллисекунды epoch |
| `durationMs` | `finishedAt - startedAt` (или `createdAt`, если не стартовал) |
| `timeoutSec` | эффективный таймаут |
| `error` | класс и сообщение корневой причины |
| `result` | результат исполнения; отдаётся только `GET /v1/jobs/{id}` и sync `run` |

### Запуск

- `POST /v1/workflows/{id}/run` — синхронно. Тело: `{"async": true|false, "timeoutSec": N}`;
  `?async=true` тоже работает. При `async` — 202 и `statusUrl`; иначе ждём до
  `timeoutSec + 30` секунд и отдаём 200 (`result`), 408 (`timeout`) или 500
  (`failed`/`cancelled`). Из-за неоднозначности прерывания sync-таймаут может прийти как
  500 с `state: failed`, а не 408.
- `POST /v1/workflows/{id}/jobs` — всегда 202.

Таймаут отсчитывается **с момента submit**, а не с начала исполнения: ожидание в очереди
съедает бюджет. Значение `timeoutSec <= 0` заменяется на 600. Верхней границы нет.
`DAP_JOB_TIMEOUT` задаёт значение по умолчанию для процесса.

### Отмена и пределы

- `DELETE /v1/jobs/{id}`: 200 для активного job, 409 для завершённого/неизвестного
  (неизвестный — 404). Отмена best effort: вызывается `WorkflowManager.cancelExecution()`
  и `Future.cancel(true)`; узел, игнорирующий прерывание, может доработать.
- Одновременно активны не более **8** jobs (жёстко в `DapService`). Превышение —
  `IllegalStateException` → 500, а не 429.
- Jobs живут только в памяти. Перезапуск процесса теряет историю и результаты.
- Один worker означает честную очередь: два агента не выполняют workflow одновременно.

## 6. Сессии

Сессия — логический тенант в пределах одного процесса. Определяется так:

1. заголовок `X-DAP-Session`;
2. иначе query-параметр `?session=`;
3. иначе `default`.

Допустимый формат: `[A-Za-z0-9._-]{1,64}`. Иначе 400 `invalid session id`. Валидная сессия
возвращается в заголовке ответа `X-DAP-Session` (для всех маршрутов, кроме `GET /v1`).

Изоляция:

| Объект | Изоляция |
|---|---|
| Workflow | список и доступ фильтруются по сессии; чужой `wf` → 404 |
| Job | `get/list/cancel` фильтруются по сессии; чужой `job` → 404 |
| Лимит workflow | `DAP_MAX_WORKFLOWS` (по умолчанию 100) на сессию |
| Имена workflow | не уникальны; идентификатор глобальный `wf-N` |
| Кэш схем диалогов | **общий** для процесса (ключ — id узла) |

Сессия не является аутентификацией: любой клиент может назваться любой сессией. Это
механизм разделения состояния, а не безопасности.

## 7. Каталог и схемы

### Каталог

`NodeCatalog` обходит extension point `org.knime.workbench.repository.nodes`, для каждого
`factory-class` грузит бандл, инстанцирует фабрику и модель, собирает:

- `id` (class), `name`, `category`, `contributor`, `type`, `configurable`, `deprecated`;
- `inPorts`/`outPorts`: `index`, `name`, `type`;
- `settings` (ключи) и `settingsXml` (умолчания), либо `settingsUnavailable`.

Результат кэшируется в `catalog/catalog.json` (формат версии 7). Если кэш отсутствует или
версия другая — каталог строится на старте (дорого). `GET /v1/nodes` ищет по подстроке в
`name + id + category` (токены AND), фильтрует по префиксу категории, по умолчанию отдаёт 50.

### Схемы

`catalog/schemas/<node-id>.json` — предрасчитанный результат `SchemaAudit`. На запрос
`GET /v1/nodes/{id}/dialog`:

1. если файл есть — он отдаётся как есть, с `precomputed: true` и актуальным `tier`;
2. если файла нет — схема строится «вживую» через `DialogSchema` и кэшируется в памяти;
3. если узел не отдал ни аннотированную, ни Swing-схему — `available: false` и `reason`,
   а настройки предлагается брать из `settingsXml`.

Предрасчитанные файлы неизменяемы на время жизни процесса: после `make build-catalog`
нужен перезапуск сервиса.

### Два вида схем

| `schemaKind` | Источник | Особенности |
|---|---|---|
| `annotations` | новый `NodeParameters` | поля, `configKey`, типы, умолчания, enum-choices |
| `swing` | старый `NodeDialog` | поля из `DialogComponent`; если диалог собран вручную — дерево `ui` без выдуманных ключей |

У Swing-схемы `fields` может быть пустым, а реальные элементы лежать в `ui`. Это не ошибка:
ключи настроек всё равно берутся из `settingsXml` узла.

### Динамические choices

`DialogSchema` умеет вызвать `ChoicesProvider` без UI:

- в контексте `GET /v1/nodes/{id}/dialog` входных таблиц нет: `ColumnChoicesProvider`
  получает `choicesNote`, зависимые провайдеры — `choicesError` или пустой список;
- в контексте `GET /v1/workflows/{id}/nodes/{node}/dialog` собираются реальные spec-ы
  входных портов (включая уже исполненные источники), поэтому варианты по колонкам
  становятся доступны.

Провайдеры, читающие другие поля через `StateProviderInitializer`, получают no-op
инициализатор: статические варианты работают, зависимые честно помечаются ошибкой.

### Настройки

`SettingsMerge` принимает JSON **по структуре XML** настроек узла: вложенные `config` —
объекты, `entry` — скаляры, повторяющиеся числовые `config` — массивы. `configKey` из
схемы диалога — это ключ `@Persist`, он не гарантированно совпадает с XML-ключом; при
ошибке сервис возвращает список доступных ключей из `settingsXml`. Настройки применяются
поверх живой секции `model` и затем `resetAndConfigureNode`.

Пустые list-массивы (`array-size=0`) поддерживаются: для них создаётся `entry` с типом
по значению. Для отдельных вложенных списков, сериализованных как numeric `config` без
шаблона, всё ещё возможен 400 `has no template to extend`; актуальные SKIP-проверки и
причины — в `tests/README.md`.

## 8. Tiers

`catalog/curated.json` содержит массив `core` (141 id; curated — источник истины).
`Tiers.apply` проставляет `tier` каждому узлу в памяти: `core` или `experimental`. Tier:

- не запрещает вызов;
- не меняет маршрутизацию;
- означает обещание поддержки и качество схемы/тестов.

`experimental` — 691 узел, включая 99 без схемы и 21 с `settingsUnavailable`.
Детали и процедура добавления — [docs/NODES.md](docs/NODES.md).

## 9. Почему один JVM-монолит

KNIME спроектирован как in-process OSGi-приложение. Его контракты (`NodeFactory`,
`NodeModel`, `BufferedDataTable`, `WorkflowManager`, `NodeParametersInputImpl`) не являются
сетевыми API. Разделение на микросервисы потребовало бы:

- сериализовать таблицы между процессами (дорого и меняет семантику типов/missing values);
- держать копию OSGi-реестра и классов узлов в каждом процессе;
- строить RPC для рефлексии по диалогам, которая сейчас работает в том же class space;
- синхронизировать жизненный цикл workflow между процессами.

Поэтому границы проведены иначе:

1. **HTTP `/v1` — единственный публичный контракт.** Внутренние классы не являются API.
2. **MCP — только транспорт.** Он не знает про KNIME и не выполняет вычислений.
3. **Каталог и схемы — артефакты сборки.** Их можно пересобрать, не меняя движок.
4. **Engine-бандл изолирован.** `com.dap.engine` зависит только от публичных API KNIME;
   это точка, где возможна замена runtime (см. INDEPENDENCE).
5. **Один процесс — одна машина.** Масштабирование — несколькими экземплярами с разными
   портами/данными, а не потоками внутри одного JVM.

Границы, которые протекают наружу и должны считаться рисками:

- рефлексия в `SwingDialogSchema` и `NodeParametersInputImpl` (внутренние классы KNIME);
- версии бандлов и формат `settingsXml`;
- абсолютные пути в `runtime/knime/configuration` (генерируются
  `scripts/gen-bundles-info.py`);
- производный статус кода под GPLv3.

## 10. Отказы и деградация

| Ситуация | Поведение |
|---|---|
| Нет `catalog.json` | каталог строится при старте (долго), затем кэшируется |
| Нет файла схемы | live-построение и кэш в памяти |
| Схема недоступна | `available:false` + `reason`; fallback на `settingsXml` |
| Нет таблицы на порту | 400 со списком портов |
| Порт не таблица, но таблица есть на другом | молчаливое переключение на первый табличный порт |
| Ошибка настроек | 400; узел мог остаться добавленным |
| `WorkflowManager` не инициализировался | 500 `NoClassDefFoundError` до перезапуска JVM |
| Перезапуск | workflow/jobs теряются; сохранённые через `save` — остаются |

## 11. Эволюция

Отделение от KNIME — не одномоментный рефакторинг, а программа с этапами, рисками и
критериями. Она описана в [docs/INDEPENDENCE.md](docs/INDEPENDENCE.md). Архитектурная
предпосылка: HTTP-контракт и формат каталога/схем стабильны, поэтому замена исполняющего
слоя не должна менять API.
